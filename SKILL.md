# Z Website Production

## Establish the artifact and authority

A build request requires a usable site or preview; a plan alone completes only a planning request.
Read the [shared contract](references/website-contract.md).
Confirm audience, goal, offer, requested pages/change, protected content and destination.
Use existing approvals; default to a preview unless the specific release is authorized.
Name the actual platform operator and project location.
Classify Simple, Structured or Managed delivery independently from inspection depth.
A typo stays small; shared components require broader dependent checks.
Done when the output, scope, owner and permitted next action are clear.

## Confirm execution capability

Use the [runtime guidance](references/runtime.md).
Verify the assigned operator can read, edit, preview, test, inspect permitted receipts and recover.
Check reusable-component behavior and release capability when relevant.
Respect the chosen platform; do not invent a new connector or hosting system.
If access is missing, finish the portable specification and exact capability handoff.
Report the build incomplete rather than calling that specification a completed website.
Done when an authorized execution path exists or its precise gap is reported.

## Plan only what the job needs

Use [website criteria](references/website-criteria.md) and the [Brief](assets/website-brief.md).
For a small edit, reuse the existing plan; inspect, change and retest affected dependencies.
For a new structured build, map visitor tasks, pages, menus, copy and next actions.
Give each page and section a purpose; avoid a universal sales-page formula.
Plan heroes, headlines, proof, mobile behavior and useful media.
Verify changeable facts and retain font/image rights evidence.
Specify page/section/header/footer templates, fields, variants and shared versus local content.
A linked global component differs from a copied starter.
Portable specifications do not promise native template import.
Done when the operator can produce the representative page without guessing.

## Build and preserve

Use Analysis only for a material learning gap; do not research during a two-line correction.
Keep editable sources and a suitable prior version.
Prove a representative page and shared header/footer before expanding a new build.
Apply authorized changes through the named operator; preserve approved copy and assets.
Keep exact words, logos and actions editable; use media specialists only when needed.
For URL changes, map old to new, check permitted redirects, internal links and preferred addresses.
Apply basic SEO and answer-ready content without installing tracking or advanced audit tooling.
Done when the requested artifact exists and can be inspected.

## Review and correct

Always perform the acceptance checks relevant to the actual change.
Prefer Critique for structured/client-facing work when available.
If separate review is required by the brief, keep it open until the named or authorized equivalent reviewer passes it.
Otherwise a documented self-review using the criteria may complete standalone work.
Label the review method honestly; never claim an unavailable skill ran.
Use [review and release rules](references/release.md).
Retest affected responsive states, interactions, shared instances and visitor paths.
Test submissions only within the recorded account/data/recipient/cleanup permission.
Confirm actual permitted receipt; a success banner alone leaves delivery pending.
Apply bounded corrections and retain finding IDs and retest evidence.
Done when required checks pass or the exact unresolved limitation is reported.

## Release only within authorization

Separate Working Draft, Review Draft, Approved for named next step and Published/Delivered.
A critique verdict is not release permission.
Before a material release record exact version, approving person, target, prior version and recovery.
Use the least destructive authorized recovery; do not erase new enquiries/orders with a database restore.
Recheck the actual public artifact and affected journeys after an authorized launch.
Stop for new material risk, missing access, unapproved cost/action or repeated failure.
Done when the requested preview/delivery or authorized public release is verified.

## Complete and maintain

Use the [Completion Record](assets/completion-record.md).
Simple edits need a change summary, exact artifact/source, relevant checks and unresolved issues.
Structured builds also retain the brief, content map, assets, template specification and review record.
Managed work adds named impact/recovery responsibilities without unrelated governance.
Record review method, finding dispositions, authority, source location and meaningful outcome signal.
Without outcome evidence say business impact unmeasured.
For assigned maintenance, inspect current state, change, retest and update the record.
Name an update owner and review trigger; cadence exists only when recurring work was requested.
Send the requester the usable result and its actual status, not just a completion claim.
